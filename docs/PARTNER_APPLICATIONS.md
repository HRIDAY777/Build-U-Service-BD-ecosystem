# Private partner onboarding

## Private renewal notifications

Renewal reminders are stored in the existing account Notifications inbox. `check_partner_renewals` creates one reminder per active document/expiry date within 30 days or already expired, only for the latest approved application of a still-approved organization in an active division. The organization must still belong to that active applicant. Newer approved renewals supersede older reminder candidates. Withdrawing a file, removing approval, transferring ownership or disabling the applicant prevents new reminders; existing delivered messages remain historical.

The applicant can use Check renewal reminders (`POST /api/v1/partner-applications/check-renewal-reminders/`); it checks only the signed-in user's applications, including for staff, and ignores client-supplied user IDs. Messages are visible in `/account` → Notifications. A unique document/date constraint and atomic reminder/message write prevent duplicate reminders and allow failed writes to retry without leaving a misleading sent record. Deleting an inbox message does not recreate it on the next scan. No repeated daily escalation is sent for the same document/date.

Celery Beat registers `apps.catalog.tasks.dispatch_partner_renewal_alerts` every 86,400 seconds. Automatic execution requires configured Redis, worker and Beat services; registering this schedule is not evidence of a running production scheduler. The button works without Redis. Reminders do not send external messages, change business approval, extend expiry or certify document authenticity. External delivery, scanning and suspension policy remain separate gates.

The private list supports `search` (up to 160 characters: business name, area, phone or verification reference), `status` and `kind` (initial/renewal). Filters are applied after owner/reviewer permissions and preserve pagination. The bilingual page provides Apply/Clear filters and a matching count; applying filters resets to page one. Invalid filters return validation errors. These parameters affect list results only and cannot widen detail/document access.

Document API responses include an `expiry` summary computed on the Bangladesh local date: expired, due_today, expiring_soon (1–30 days), valid (over 30 days), not_provided, or withdrawn. It includes days_remaining, as_of and renewal_needed. The application page shows bilingual expiry/renewal notices; use Refresh for a current snapshot. The 30-day window is an informational reminder, not a statutory deadline. Missing expiry is displayed as unknown, not proof of validity. Withdrawn documents do not trigger renewal notices. The notices do not automatically renew files, send notifications or suspend businesses.

## Renewal submissions

The applicant can select Open renewal application on an approved application (`POST {id}/renew/`). The organization must still be approved, in an active division and owned by that applicant. A new submitted application links to the approved record via read-only `renewal_of`; previous documents/decisions are not copied or altered. Repeated requests return the same open renewal across approved records for that organization. Cancelling or rejecting a renewal allows another attempt. Business identity/division/address are frozen on renewal; contact number and explanatory details may be updated. A renewal decision does not change the business profile.

Upload new documents, then follow the existing reviewer workflow. Every active replacement must be accepted and unexpired before approval. Approval links the renewal to the same organization, without creating another organization or restoring a suspended/transferred business. Each approved record can initiate a later renewal. Migration `catalog.0013` changes the organization link from one-to-one to foreign key and adds the protected renewal source, preserving existing data. Application/organization row locks guard repeated requests on databases that support them; PostgreSQL concurrency has not been certified locally. Historical approved records remain visible with their original expiry dates.

Renewal approval is a manual document decision, not proof of legal compliance. Automated monitoring, external notifications, suspension policies, specialist licensing, malware scanning and retention still require separate work. Generic new-application requests cannot set `renewal_of` or an organization.

Applicants sign in at `/partner-application`, submit a business division/name/contact/address, and upload up to ten private PDFs (5 MB each). No bank details or national ID are requested. Applicants can edit, withdraw a document, or cancel only while submitted or changes are requested. Editing resubmits the application; upload alone does not resubmit requested changes.

Reviewers need both `catalog.view_partnerapplication` and `catalog.change_partnerapplication`. A staff flag alone does not provide access. Superusers already have these permissions. Grant both only to authorized business reviewers; ordinary organization edit permission is insufficient. Django admin displays these records read-only. Decisions are made through the application page/API.

Review flow: submitted → reviewing → approved / rejected / needs_changes. Reviewers cannot review their own applications or documents. While reviewing, inspect each active document and record accepted/rejected with a required note. Decisions have a timestamp and an audit record linking reviewer, decision, note and file hash; raw reviewer identity is not exposed in applicant API output. Acceptance of an expired document is blocked. Approval requires at least one active document, every active document individually accepted, no expired active documents, an application note and verification reference. Approval creates a new approved organization owned by the applicant; it cannot claim or alter an existing organization, grant staff privileges, or execute payments. Approved/rejected/cancelled applications and document decisions are frozen. Business approval is not specialist licensing, pharmacy clearance, or proof of regulatory compliance.

Endpoints under `/api/v1/partner-applications/`: paginated own list/detail (authorized reviewers see all), create, PATCH, `capabilities/`, `cancel/`, `document/`, `documents/{id}/download/`, `documents/{id}/withdraw/`, and `review/`. Private downloads are attachment-only with no-store/nosniff headers. API output excludes storage URLs and owner identity. Mutations are audited; transitions lock the application in a database transaction. Approval cannot be replayed to create a second organization. Withdrawn files are retained for the audit trail and ignored for approval; they count toward the ten-document limit.

Document decisions use `POST documents/{id}/review/` with `status` (accepted/rejected) and required `note`. Withdrawn documents cannot be reviewed and do not count toward the approval gate. Corrections require the applicant to withdraw the rejected file, upload its replacement and resubmit. Every replacement starts pending. Migration `catalog.0012` sets existing document decisions to pending without changing previous application/organization approvals; it does not retroactively certify old files or revoke businesses.

Local file validation checks size and PDF header, not malware or document authenticity. Private production storage/scanning/retention policies, renewal monitoring and suspension after expiry, specialist reviewer eligibility, automatic notifications, searchable geography and duplicate-submission idempotency remain separate improvements. This milestone must not be presented as a complete regulated partner verification system.

Verification: backend tests cover private scope (including unauthorized staff), self-approval denial, document privacy, invalid files, expired-document replacement, guarded approval, preservation of existing businesses and terminal immutability. Browser coverage submits an actual test application/PDF, downloads privately, reloads and cancels; it does not certify uploaded content or legal review.

## Private application history

GET history/ on an application is owner/reviewer scoped, paginated (24), newest first and no-store. It exposes only event/date/generic actor and a validated decision status. Raw audit metadata, file hashes, filenames, review notes and reviewer identities remain private. The bilingual application card loads history on expansion, supports paging and refresh, and shows upload/cancellation events. Backend tests verify cross-account denial, redaction, malformed metadata and pagination; real browser coverage checks submission/upload/cancellation and refresh.
